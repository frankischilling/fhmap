# fhmap

`fhmap.h` is a fast, compact, single-header hash map for C11 on Linux. It
stores fixed-size keys and values inline, performs no allocation per entry, and
uses a SwissTable-style control-byte array so most failed lookups never touch
key or value storage.

The library is intended for systems code, games, compilers, caches, and tools
that need a simple C map without a dependency tree. It is engineered for high
throughput and predictable memory use; benchmark it with your own key types and
workload before making absolute performance claims.

## Highlights

- One header and no runtime dependencies beyond libc
- One allocation for the entire table; zero allocations per inserted element
- 16 control bytes examined at once with SSE2 on x86-64
- Portable scalar fallback for other Linux targets
- 87.5% maximum load factor
- Seeded, 64-bit, non-cryptographic byte hash with fast 4/8/16-byte equality
- Typed wrappers generated by one macro
- Raw API for custom hash/equality functions and borrowed string keys
- Tombstone cleanup, explicit reserve/compact operations, checked arithmetic,
  and allocation-failure propagation
- Tests, fuzz-style differential checks, sanitizers, and a standalone benchmark

## Add it to a project

Copy `fhmap.h` into your source tree. In exactly one translation unit:

```c
#define FHMAP_IMPLEMENTATION
#include "fhmap.h"
```

Every other translation unit includes it normally:

```c
#include "fhmap.h"
```

The default build target is C11 and Linux. GCC and Clang are supported.

## Typed API: five-minute example

Declare a map type at file scope:

```c
#include <inttypes.h>
#include <stdio.h>

#define FHMAP_IMPLEMENTATION
#include "fhmap.h"

FHMAP_DECLARE(score_map, uint64_t, int);

int main(void)
{
    score_map scores;
    const uint64_t *id;
    int *score;
    score_map_iter it;

    if (!score_map_init(&scores, 1024)) {
        fputs("out of memory\n", stderr);
        return 1;
    }

    score_map_put(&scores, 1001, 88);
    score_map_put(&scores, 1002, 93);

    score = score_map_get(&scores, 1002);
    if (score != NULL) printf("score = %d\n", *score);

    it = score_map_iter_begin(&scores);
    while (score_map_iter_next(&scores, &it, &id, &score)) {
        printf("%" PRIu64 " => %d\n", *id, *score);
    }

    score_map_destroy(&scores);
    return 0;
}
```

Compile it:

```sh
cc -std=c11 -O3 -march=native example.c -o example
```

`score_map_init(&scores, 1024)` reserves room for at least 1,024 elements. It
does not mean 1,024 raw buckets. `score_map_init_seed` accepts an explicit seed
when deterministic layout is useful in a benchmark or reproducible build.

## Avoid the value copy

`emplace` returns the map's value storage. On a new key the storage is
uninitialized, which is useful for large values:

```c
bool inserted;
struct record *record = record_map_emplace(&records, id, &inserted);
if (record == NULL) {
    /* allocation failure */
}
if (inserted) {
    *record = make_record(id);
}
```

## String keys

The typed macro hashes the bytes of the key object. A `char *` key therefore
hashes the pointer value, not the pointed-to text. Use the raw configuration API
to compare string contents:

```c
fhmap strings;
fhmap_config cfg = fhmap_config_make(sizeof(const char *), sizeof(unsigned));

cfg.initial_capacity = 256;
cfg.key_align = _Alignof(const char *);
cfg.value_align = _Alignof(unsigned);
cfg.hash = fhmap_hash_cstr;
cfg.equal = fhmap_equal_cstr;

if (!fhmap_init(&strings, &cfg)) {
    /* allocation failure */
}

const char *key = "violet";
unsigned value = 7;
fhmap_put(&strings, &key, &value);
```

String storage is borrowed. The text must remain alive and unchanged while its
key is in the map. If ownership is required, store offsets into your own arena
or duplicate/free strings in the surrounding application.

## Memory model

For capacity `C`, key stride `K`, and value stride `V`, the main allocation is
approximately:

```text
C control bytes + C*K key bytes + C*V value bytes + alignment padding
```

The key and value strides are their sizes rounded up to the alignments supplied
in `fhmap_config`. For ordinary C object types, `sizeof(type)` is already a
multiple of `_Alignof(type)`, so the typed API normally adds no per-slot
padding. `fhmap_memory_usage` reports the allocation owned by the table.

The key and value arrays are separate. A miss reads control bytes and only the
few keys sharing its 7-bit fingerprint; value pages stay cold until a hit.

## Correctness and lifetime rules

- Keys and values have one fixed size for the life of a map.
- A key's bytes must not change while it is stored.
- A custom equality function must agree with the custom hash: equal keys must
  produce equal hashes for the same seed.
- Pointers returned by `get`, `emplace`, or iteration are invalidated by any
  structural mutation. Updating the value of an existing key is not structural.
- Do not pass a key/value pointer that points inside the same map to an insertion
  that may grow the table. Copy it to a local object first.
- Iterators are invalidated by insert, remove, clear, reserve, or compact.
- A map is not internally synchronized. Concurrent reads are safe only while no
  thread mutates the map; synchronize writers externally.
- The default hash is not cryptographic. A randomized per-map seed makes
  precomputed collision attacks harder but does not turn it into a MAC.

## Build and verify

```sh
make test          # optimized GCC test run
make clang-test    # test with Clang when installed
make sanitize      # ASan + UBSan test run
make bench         # compile and run the benchmark
```

Pass an element count to the benchmark executable for a different workload:

```sh
./build/bench_fhmap 5000000
```

The benchmark prints insert, successful lookup, failed lookup, iteration, and
erase throughput plus table allocation size. CPU, compiler, flags, key
distribution, and load factor can change results substantially.

## Configuration

Define options before including the implementation:

| Define | Effect |
|---|---|
| `FHMAP_STATIC` | Give the raw API internal linkage |
| `FHMAP_DISABLE_SIMD` | Use the portable scalar group scanner |
| `FHMAP_MALLOC(user, size)` | Replace allocation |
| `FHMAP_FREE(user, ptr)` | Replace deallocation |
| `FHMAP_MAX_ALIGNMENT` | Maximum accepted key/value alignment (default 4096) |

Allocator macros receive `fhmap_config.user`, so an arena or allocator context
can be supplied without global state. Allocation must return storage suitable
for ordinary byte access; `fhmap` performs its own in-block alignment.
